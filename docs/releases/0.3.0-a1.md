# DAPPER 0.3.0-a1

This alpha restructures the schema into concept modules and flattens the
repository layout. It also adds evidence that grounds in the exact bytes of a result file,
and a common, versioned `Collection` base with a new `ResultCollection` for
analysis results. These additions were developed as 0.2.1-a1, which was never
tagged, and ship here instead.
It also replaces the DISMECH pointer fields with an optional correspondence
edge, frames scientific accounts with Questions, KnowledgeGaps and
Hypotheses, moves ancestry and trait into typed contexts, and defines
causality once, as interventionist causal graphs. The identity
profile is still DAPPER-ID-1 and its frozen vectors reproduce. Identifiers
change only for records that use a reshaped field, and for the records that
reference them. It is a schema and tooling snapshot; there is no Python
package to install.

## Schema modules

`schema/dapper.yaml` stays the entry point, but it now only imports the
modules below and defines no classes. Every module is linted on its own.

| Module | Holds |
|---|---|
| `core.yaml` (new) | What is tracked: the graph skeleton (`Node`, `HashableNode`, `Edge`), identity, attribution and provenance, files, DRS and DUO, embeddings, and the collection classes and `ValueLocator` below. Importable alone. |
| `claims.yaml` | Scientific reasoning: `Proposition`, `Claim`, `ClaimScore`, `EvidenceItem` (moved here), the framings (`Framing`, `Question`, `KnowledgeGap`, `Hypothesis`), `ScientificAccount`, `Paragraph`, the abstract `ExplanatoryModel`, and the causal classes (`CausalVariable`, `CausalLink`, `CausalGraph`). Imports only `core`. |
| `genesets.yaml` (new) | `GeneSet`, `GeneSetCollection`, `has_gmt_file`. |
| `cell_programs.yaml` (new) | `GeneProgram` and its quality score, `CellState`. |
| `mechanisms.yaml` (new) | `MechanisticModel` (now `is_a: CausalGraph`), `MechanisticLink`, `Mechanism`. |
| `scm.yaml` (new) | `StructuralCausalModel` (a `CausalGraph`) and `CausalEstimand`. |
| `nanopub.yaml` (new) | The nanopublication quad, signature, lifecycle edges and `AssertedIn`. |
| `dismech.yaml` (new) | `CorrespondsToDismech`, the optional DISMECH correspondence edge, and the pathograph projection table. |
| `replay.yaml` (new) | `AgenticWorkspace`. |
| `cfde.yaml` (new) | `C2M2File`. |
| `biology.yaml` (new) | The biological kinds of the core `Context`: `AncestryContext`, `TraitContext`, `TissueContext`, `CellTypeContext`, `CellLineContext`, `OrganismContext`, and `AncestryEnum`. |

Class names, slots, and identifiers are unchanged by the split. Only the
module that defines each class moved. One structural change keeps the
reasoning layer free of domain imports: the `mechanistic_model` slots on
`Proposition`, `ScientificAccount` and `EvidenceItem` now range over the
abstract `ExplanatoryModel`, which `MechanisticModel` specializes, and are
renamed `explanatory_model` (see Causality). Records that used the slot are
re-minted.

## DISMECH correspondence

DAPPER no longer builds DISMECH pointers into its records.

- **Removed:** the `DismechLinked` mixin and its four hashed fields
  (`dismech_class`, `dismech_entry_key`, `dismech_disease_term`,
  `dismech_source_url`) on `Dataset`, `Claim`, `MechanisticModel`,
  `CausalStep` and `Mechanism`. Because they were hashed, adding a DISMECH
  link used to change a record's id.
- **Added:** a general `CorrespondsTo` edge in core (any node to an entry in
  another resource, `skos:closeMatch` by default), and `CorrespondsToDismech`
  in `dismech.yaml`, which adds `dismech_class` and `entry_key`. Edges are not
  part of a node's identity, so correspondences can be added or removed
  freely. Point `object` at the disease's DISMECH page and name the entry on
  it in `entry_key`; a disease ontology term is not the DISMECH entry.
- **Parity stays as mappings**, on classes outside the general causal layer:
  `MechanisticModel` ~ `dismech:MechanisticHypothesis`, `MechanisticLink` ~
  `dismech:CausalEdge`, `Mechanism` ~ `dismech:Mechanism`, and the existing
  mappings on Framing and EvidenceItem. All are `close`: DAPPER owns the
  definitions.
- **Pathograph projection:** `tools/dismech_pathograph.py` maps a DISMECH
  disease file onto causal graphs and back. All 2,948 disease files in a local
  DISMECH checkout round-trip with identical edge sets. Edge evidence is not
  projected yet.
- The linter accepts `external` as an edge endpoint in `lint/profiles.yaml`,
  and an edge class inherits its nearest ancestor's endpoint rule.

## Framing: questions, knowledge gaps and hypotheses

- **New:** abstract `Framing` in claims, with three siblings: `Question`,
  `KnowledgeGap` (no longer a subclass of Question) and a new `Hypothesis`
  that references the Proposition it puts forward. `Hypothesis` carries no
  statement, assessment or mechanism of its own, unlike the class retired in
  0.2.0.
- **Changed:** `ScientificAccount.question` and `.hypothesis` are replaced by
  one required, ordered `framing` list. New document group: `hypotheses`.
- **DISMECH:** `Framing` and `KnowledgeGap` close-match `dismech:Discussion`;
  `GapKindEnum` close-matches `dismech:DiscussionKindEnum`.
- **New:** `ScientificAccount.identified_gaps` lists the KnowledgeGaps an
  account finds, such as the critical untested link of its model, and
  `KnowledgeGap.concerns` names the Propositions (often one CausalLink) whose
  truth is the missing knowledge. Framing is what an account sets out to
  address; identified gaps are results, which a later account can take as
  its framing.
- Question and KnowledgeGap ids are unchanged. Accounts, and the paragraphs
  that express them, are re-minted.

## Causality

One definition, used throughout: X causes Y in a context when some
intervention on X would change Y there. See the
[causality guide](../guides/causality.md).

- **New in claims:** `CausalVariable` (an entity plus the aspect that
  varies), `CausalLink` (a kind of `Proposition`: cause, effect,
  `effect_direction`), and `CausalGraph` (an `ExplanatoryModel` over an
  explicit `variables` set, with `links` and `has_feedback`). Claims and
  EvidenceItems can address one link at a time.
- **Directness moved to the graph.** A link's `link_type`
  (`CausalLinkTypeEnum`, moved here from mechanisms) and `intermediates` sit
  on its `CausalGraphLink` entry, so one link keeps one id in every graph.
- **Feedback is declared.** A graph is a DAG unless `has_feedback: true`; an
  undeclared cycle is an error.
- **Controlled link content:** `CausalVariable.aspect` is `AspectEnum`
  (what changes), and `CausalLink.causal_relation` is `CausalRelationEnum`
  (`CAUSES`, `CONTRIBUTES_TO`, `ENABLES`, `REGULATES`), alongside
  `effect_direction` (which way).
- **Structural causal models** (`scm.yaml`): `StructuralCausalModel` adds
  per-variable domains, latent variables, distributions and structural
  equations to a CausalGraph; `CausalEstimand` names a causal quantity in a
  model, and estimates are Claims with `EFFECT_ESTIMATE` scores. New document
  groups: `structural_causal_models`, `causal_estimands`.
- **New vocabularies:** `Proposition.relation_kind` (`ASSOCIATION`,
  `PREDICTION`, `MEASUREMENT`, `CONSTITUTION`, `CAUSATION`),
  `EvidenceItem.evidence_design` (`EXPERIMENTAL_INTERVENTION`,
  `NATURAL_EXPERIMENT`, `OBSERVATIONAL`, `MECHANISTIC`, `COMPUTATIONAL`).
  Propositions also take typed `contexts`.
- **Mechanisms:** `MechanisticModel` is now a `CausalGraph`; its
  `MechanisticLink` entries may name `via_mechanism`. `CausalStep`,
  `HasCausalStep`, `has_causal_step`, and the model's `subject_entity` /
  `object_entity` are removed. New document groups: `causal_variables`,
  `causal_links`, `causal_graphs`; `causal_steps` is gone.
- **Renamed:** the `mechanistic_model` slot on `Proposition`,
  `ScientificAccount` and `EvidenceItem` is now `explanatory_model`, since it
  accepts any `ExplanatoryModel` (a causal graph, mechanistic model or
  structural causal model).
- The Dent example is rebuilt as four variables and three links, and the
  example propositions carry a relation kind; affected records are re-minted.

## Contexts

- **New in core:** an abstract `Context` value class and a `contexts` list on
  Dataset and Activity (through the `Contextual` mixin). Each entry names its
  kind in `context_type`. Core says only that records can have contexts; the
  kinds live in domain modules.
- **Moved to `biology.yaml`:** `AncestryContext` and `TraitContext` (now
  `is_a: Context` classes rather than mixins), the `ancestry` and `trait`
  slots, and `AncestryEnum`, with the `HANCESTRO` and `KPN.TRAIT` prefixes.
- **Data shape:** `ancestry: AA` and `trait: KPN.TRAIT:0000096` on a record
  become `contexts: [{context_type: AncestryContext, ancestry: AA},
  {context_type: TraitContext, trait: KPN.TRAIT:0000096}]`. Records that
  stated either are re-minted.
- **New kinds:** `TissueContext` (`tissue`, UBERON), `CellTypeContext`
  (`cell_type`, CL), `CellLineContext` (`cell_line`, Cellosaurus written
  `cellosaurus:0025`, CLO or EFO) and `OrganismContext` (`organism`,
  NCBITaxon). Each names one ontology term, not an enum value, so the
  ontology hierarchy stays usable; look terms up (for example in the EBI
  Ontology Lookup Service) rather than recalling them. `trait` also accepts
  MONDO and EFO terms. New prefixes: `EFO`, `UBERON`, `NCBITaxon`, `CLO`,
  `cellosaurus`, and `biolink` in core. `HGNC.SYMBOL` stays a per-document
  prefix (the claims repository maps it to `https://identifiers.org/hgnc.symbol:`).
- **Where contexts go:** Propositions (including CausalLinks), causal graphs,
  and now `EvidenceItem`. An EvidenceItem's contexts say where its evidence
  was obtained; when they differ from its target proposition's, the evidence
  bears on the proposition by analogy (mouse for human, a cell line for a
  cell type).
- **Linter:** at most one context of each kind per record (error), sorted by
  `context_type` because order is part of identity (warning). The
  trait-dimension check on result collections and `lint_dig_ancestry.py`
  read the contexts.

## Changes

- **`ValueLocator`** pins one serialized value inside a File: the byte span,
  the value as read (`value_text`), a readable selector and the media type. A
  verifier checks the File's sha256, then compares
  `file[byte_start : byte_start + byte_length]` with `value_text`.
- **`EvidenceItem.value_locators`** grounds evidence in result-file values.
  `source_claims` is now optional, so evidence read from a file needs no
  synthetic intermediate claim. Evidence with locators must name its
  `target_proposition` and give an `explanation`. `direction` stays optional
  unless `source_claims` is also present.
- **`Collection`** (abstract) is a `Set` whose members are other DAPPER
  records. It adds optional versioning: `collection_key`, shared across
  versions; `version`; and `was_revision_of`, which chains each version to the
  one before. `GeneSetCollection` now inherits from it, so gene-set libraries
  can be versioned too, and `ResultCollection` is new.
- **`ResultCollection`** is one immutable version of a named collection of
  analysis results. Its `members` are Datasets. It also lists the claim and
  query template Files and the manifest File it was built from, and records
  `methods` and the `dataset_dimensions` that identify each Dataset.
  `collection_key` and `version` are required. Claims do not reference the
  collection, so a new version re-addresses only the claims whose template or
  file changed.
- **`Dataset.dimension_values`** and **`Dataset.file_roles`** place a Dataset
  in its collection, e.g. `{trait: KPN.TRAIT:0000505, library: cfde-inc-v2}`
  with its `gene_stats` file. Both are inline value objects (`DimensionValue`,
  `FileRole`) that contribute to the Dataset's identity.
- **Linter.** A new `result-collection` profile. New checks that member
  Datasets give every dimension in order, that no two Datasets share all
  dimension values, that a `trait` dimension agrees with the Dataset's `TraitContext`,
  that role files are in `has_file`, and that `n_members` matches. For any
  Collection, `was_revision_of` must stay within one class and one
  `collection_key`. An earlier version in the same document counts as
  upstream (`prov:wasRevisionOf` is a derivation). The linter warns when a
  version lists more than one method, or when a member file came from a method
  it does not list.
- **Docs and examples.** A [result collections guide](../guides/result-collections.md),
  including why mixing methods in one collection is usually an anti-pattern,
  and a [Croissant guide](../guides/croissant.md) for importing
  [Croissant](https://mlcommons.org/working-groups/data/croissant/) records
  into DAPPER and publishing DAPPER results as Croissant, using existing
  classes only. Its worked example is a Croissant 1.0 record that `mlcroissant`
  loads. A test checks every `FileObject` against the matching DAPPER `File`
  by sha256.
  Two synthetic examples whose NDJSON result files are real bytes, so their
  locators are verified in tests. The portal shows both.

## Migration from 0.2.0

- Move paths as in the layout table above. Schema imports are unchanged:
  import `dapper` as before, or `core` alone.
- The frozen DAPPER-ID-1 vectors still reproduce, and the new Dataset and
  Collection slots hash only when present. Identifiers change only for
  records that used a field this release removes or reshapes, and for the
  records that reference them; re-run `identity/dapper_identity.py assign`.
- Move any `dismech_*` fields off a record into a `corresponds_to_dismech_edges`
  entry (`subject`: the record, `object`: the disease's DISMECH page, plus
  `dismech_class` and `entry_key`), then re-mint.
- Rename `mechanistic_model` to `explanatory_model` on Propositions,
  ScientificAccounts and EvidenceItems, then re-mint.
- Replace each `CausalStep` with a `CausalLink` between two
  `CausalVariable`s (say which aspect of the entity varies), and list it in
  the model's `links` with its `link_type`. `step_index` has no counterpart:
  order follows from the graph. List the model's `variables`, and set
  `has_feedback` if it has a loop.
- Replace `ScientificAccount.question` and `.hypothesis` with an ordered
  `framing` list: keep the Question or KnowledgeGap id, and wrap a hypothesis
  Proposition in a `hypotheses` record (`proposition: <id>`) and list that.
- Move a record's `ancestry` / `trait` into `contexts`, sorted by
  `context_type`: `{context_type: AncestryContext, ancestry: AA}`,
  `{context_type: TraitContext, trait: KPN.TRAIT:0000096}`.
- Re-mint every changed document with `identity/dapper_identity.py assign`,
  and update references held in other documents.
  `GeneSetCollection` moved from `is_a: Set` to `is_a: Collection`, which is
  itself a Set, so it keeps every slot it had.
- Documents that minted ValueLocators against the uncommitted proposal (group
  key `value_locators`) are valid as written. The class, its fields and their
  hashability are unchanged.
- Evidence that grounds only in `value_locators` must have
  `target_proposition` and `explanation`. Re-mint after adding a missing
  explanation, since it is a hashed field.
- `ResultCollection` and `GeneSetCollection` are siblings. A gene-set library
  stays a `GeneSetCollection`. When results are sliced by library, the library
  is a result-collection dimension.
- The `collection` alias moved from `Set` to `Collection`.

## Pull and validate

```sh
git clone --branch 0.3.0-a1 https://github.com/broadinstitute/dapper.git
cd dapper
uv run lint/lint_provenance.py \
  examples/example_result_collection.yaml --strict
uv run --with-requirements tests/requirements.txt pytest tests/ -q
```

The pre-commit hooks (`prek run`: `linkml-lint` with no warnings, then the
full test suite) pass. Run with `--with-requirements tests/requirements.txt`,
`test_model_uris.py::test_imported_type_native_links_resolve_after_documentation_merge`
fails, on 0.2.0 too. It checks how the LinkML documentation generator merges
imported types, and it does not affect the schema or identifiers.
